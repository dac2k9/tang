# Platform and future ideas

Part of what `CLAUDE.md` held in one piece until it was split (2026-11-04): build requirements, CI, and the ideas that are not built. `CLAUDE.md` has the index of the reference files. The sections keep the titles and the text they had, which the other documents and the comments in the code refer to ("see ..."), and the `TODO:` lines are where they were.

## Platform

Cross-platform: Linux, macOS, Windows.

LV2 support is behind the `lv2` Cargo feature (enabled by default). The LV2
dependency chain (livi → lilv → lilv-sys) requires the `lilv` system C
library:

- **Linux**: `apt install liblilv-dev` (or distro equivalent)
- **macOS**: `brew install lilv`
- **Windows**: not supported

The upstream `lv2-sys` crate (RustAudio/rust-lv2) doesn't compile on macOS
because its `unsupported.rs` is a `compile_error!`. PR #117 fixes this with
a one-line `cfg_attr` aliasing macOS to the Linux bindings. Until that PR
merges, `Cargo.toml` patches `lv2-sys` to akx's fork (1 commit ahead, 0
behind upstream develop). Drop the `[patch.crates-io]` entry once #117 lands.

VST3 support is behind the `vst3` Cargo feature (enabled by default). It uses
pre-generated bindings (no build-time SDK dependency) and works on all platforms.

The `web` Cargo feature (off by default) is the browser front-end: `ts-rs`
(which generates the TypeScript of the protocol types), the server (`axum`,
`tokio`) and `ctrlc` for stopping `tang serve`. `tokio-tungstenite` and
`futures-util` are in it for the tests' WebSocket client (axum's `ws` is built on
the same crate). See "Web UI".

CI runs clippy + tests on all three platforms:

- **Linux** — full default features (LV2 + VST3 + CLAP), `apt install liblilv-dev libasound2-dev libjack-dev`
- **macOS** — full default features (LV2 + VST3 + CLAP), `brew install lilv`
- **Windows** — `--no-default-features --features vst3` (CLAP is not feature-gated, so it's always built; LV2 is unsupported)

Each of them then also runs clippy (`--all-targets`) and the tests with `--features
web` added, which includes `tests/serve.rs`, the real binary on `--audio-device
none`. What needs a Unix there is `#[cfg(unix)]`: the two Ctrl+C tests (they send the
signal with `kill`) and the three ignored tests that make virtual MIDI ports. The job
`typescript` checks that the generated TypeScript is current. The job `kernel` builds
and tests the workspace crate `kernel/` alone (clippy, the tests in debug and in
release) on the three platforms: it has no plugin format, sound card or interface in
it (see "The kernel"). The job `web` (Linux) runs the page's lint, types, Vitest,
production build and Storybook build, builds the program with `--features web` and
runs the Playwright suite against it (`npm run e2e`); a failed run keeps
`playwright-report` for seven days, whose traces have the values that a test read.

A `.gitattributes` (`* text=auto eol=lf`) keeps every text file LF in a Windows
checkout: the golden snapshots, the generated fixtures and the session text that tests
edit are compared as written, and CRLF failed 38 tests there. The runners are several
times slower than the machine that the tests were written on, so what waits on a clock
has a bound for them (Vitest's `testTimeout` is 30 s under `CI` and 5 s otherwise), and
a browser test of the real program reads the most of a live value over a window and
not one reading at a moment: the tracer's LFO makes the sound depend on the phase, and
a runner's timeline is steady, so that a reading that is bad at one phase is bad every
time (`e2e/master.spec.ts`, `held`).

## Future ideas

- **Tang as a plugin in a DAW** (the user, 2026-11-05, while step 112 was being started: "would be possible to add a target to be able to build this as a VST or other plugin format that we can load into a daw?"). Possible, and a project of its own, not a build flag; not started. *What helps:* the engine is separate from the sound card (`Renderer::render` in `src/audio.rs` fills a block of any length, interleaved, from a list of MIDI events: what `--audio-device none` and the tests already drive, and what a plugin's `process()` would call), a session is TOML that a DAW could keep as the plugin's saved state, and a macro has a name and an `expose` flag (steps 110 and 111), which makes it the natural automatable parameter. *Formats:* CLAP first (`clack-plugin` is in the same repository as the `clack-host` that Tang hosts CLAP with, and its extensions `audio-ports`, `note-ports`, `params`, `state`, `latency`, `timer` and `gui` are the ones this needs), then VST3 and AU by wrapping the CLAP with `clap-wrapper` (C++ and CMake; not tried with a Rust plugin); Tang hosts CLAP, so it could load its own `tang.clap` to be tested with no DAW. *What makes it big:* (1) the package is one binary crate (`kernel` and `view` are libraries), so a library and binary split comes first, a refactoring to do before the feature (`cargo test --bin tang`, which the mutation runner uses, becomes `--lib`); (2) the DAW's callback drives the engine: any block size, its sample rate and tempo (Tang has tempo and patterns of its own), the master limiter off by default, the latency reported; (3) no terminal and no main loop of ours: the controller runs on the DAW's main thread from CLAP's `timer`, and the page is served on a port for each instance (a webview window later); (4) the scan of the installed plugins in a process of its own (f179: a DAW's main thread turns its run loop all the time, and every instance that scanned at start-up would be slow); (5) the state of the plugins inside, which is part C of step 112, so that comes first; (6) a fixed bank of 16 to 32 parameters mapped to the exposed macros, since a DAW wants a fixed list. *Risks:* plugins inside a plugin (other hosts do it, each plugin's habits add up), globals that several instances share (the config's `OnceLock`, the CoreMIDI client, the catalog), and macOS signing and notarization to give the file to anyone else. The order told to the user: finish step 112, then the split and a CLAP with no interface of its own (notes in, audio out, the page in the browser); which DAW they use decides whether VST3 or AU comes second.
- **A button that opens a plugin's own window** — **step 112 parts A and B are built (the window, the VST3 view protocol and `tang window`; and the app: the page's "UI" button and menu item, the terminal's `u`, the parameters both ways: see "A plugin's own window" in `plugins.md`); part C (the state) is next** (the user, 2026-11-04, while step 111 was being finished: "for a VST, is it possible to add a button to open the "official" UI?"). Possible, and a feature of its own, not a button: Tang has no plugin GUI code at all (`docs/web-ui.md` §1 lists native plugin GUIs as a non-goal "for now"; `clack-extensions` is built without its `gui` feature). What it takes: (1) **a native window and an event loop on the main thread**: on macOS an `NSWindow` and AppKit, which a terminal program does not have (the terminal's loop or the server would move to a second thread, or the run loop would be pumped from it; `midi.rs` already pumps one for CoreMIDI, and f179 is the lesson that turning the main run loop collides with the message queue of a JUCE plugin, which the ROLI plugins are, while the catalog is scanned); (2) **the VST3 view protocol**: `IEditController::createView("editor")`, `isPlatformTypeSupported`, `getSize`, `attached(NSView)`, `IPlugFrame::resizeView`, `onSize` and `removed`, with the controller reachable from the main thread (a plugin is moved to the audio thread once it is set up: `Vst3Plugin` is `Send` and only `process` runs there); (3) **the parameters, both ways**: `TangComponentHandler::performEdit` is a stub that drops the value, so a knob moved in the plugin's own window would reach neither the sound nor the model; it has to become a parameter change for the audio thread and an event for the model (so that the page, the history and the cables agree; a cable that drives the parameter adds to it), and a change made in the page, by a preset or by a modulator has to reach the open window (`setParamNormalized`, at the window's rate); (4) **state**: Tang keeps a plugin as its id, a preset *name* and the parameters that differ, and no state (`getState`, `setState` and `IBStream` are nowhere), so what a person does in the plugin's own window that is not a parameter (a preset or a model chosen there) is not saved until the state is. By format: CLAP is the easiest (the `gui` extension with a *floating* window that the plugin makes itself; `clack-extensions` has `gui`, `timer` and `posix-fd`), VST3 needs the host's window, and LV2 needs `suil` and a toolkit (not worth it). The button would be on the node of a plugin that has a window, and the window opens on the machine that runs Tang (a browser on another machine does not get it). A first step would be one format on one platform with the window, the parameters both ways and the state decided before the button."
