# Tang as a plugin in a DAW

Part of what `CLAUDE.md` holds as a front door: the plugin that Tang is in a DAW (step 113), which is built from the same library as the `tang` program. `CLAUDE.md` has the index of the reference files. The `TODO:` lines are where this is not done yet.

### The two plugins in `Tang.clap` (step 113, `tang-clap/`, `tang::embed`)

The user's ask, after the plugin's own window (step 112) was done: "would be possible to add a target to be able to build this as a VST or other plugin format that we can load into a daw?" (2026-11-05), and, asked which DAW: **"I mainly use bitwig, on windows, so thats where I want to try it. Lets try this next."** (2026-11-06). Bitwig loads CLAP natively and co-created it, so CLAP is the format; VST3 and AU would come from wrapping it (`clap-wrapper`), and are not built.

- **What the file has.** One file, `Tang.clap`, with two plugins in it: **Tang** (`io.github.apanloco.tang.instrument`; features `instrument`, `synthesizer`, `stereo`: notes in, what the session plays out) and **Tang FX** (`io.github.apanloco.tang.effect`; `audio-effect`, `stereo`: stereo audio in, what the session makes of it out). The ids are what a host keeps a plugin by in every project that has it: **they are never changed.** Both have a stereo output, one input of notes (the MIDI dialect is the preferred one, the CLAP dialect is understood: a note-on and a note-off, and a choke as a note-off; what a CLAP note says beyond that, its expressions, is not carried over) and a window; the effect has a stereo audio input as well.
- **What a new one is.** A new Tang is one lane with the oscillator (`builtin:osc`) and a new Tang FX is one lane with the audio input (`builtin:input`, which plays what the host gives the plugin to hear: no sound card is opened) that goes to the mix, so that it passes the sound through until a person builds something in the page. **The master's limiter is out of the sound in both** (`Kind::default_session`): a host works in floating point and has headroom, and the limiter holds the sound back by 2 ms, which a host that is not told of it cannot make up for (an effect would be late against its own dry sound). A person who wants it puts it in, in the page, and then has the 2 ms.
- **The window is the page.** The host's button for a plugin's window opens the page of that instance in the browser that the person has (`gui` as a floating window that the plugin shows itself: `show` opens `http://127.0.0.1:<port>/`, `hide` does nothing, a window that is to be put in one of the host's is refused). Every instance serves its own page on a port that the system picks, on this machine only (no token is needed there). The address is in the log (`Web interface: …`) if the button does not open it; `TANG_BROWSER` says another program to open it with (it is run with the address as its one argument). **That a host shows a button for a window that only the plugin can make (a floating one) is not known**: the CLAP rules allow it and say nothing of what a host does with it, and Bitwig's was not tried. So the same thing is also **a parameter**, which every host shows: **Open the page** (below).
- **What is saved is the session.** The host's `state` is the session as the text of a session file, after nine bytes (`TANGSESS` and a version, 1) that say what it is: what a person builds in the page (lanes, effects, cables, modulators, a macro's name, the places of the nodes) and what the plugins inside keep in them (step 112, part C) go with the host's project and come back with it. State that has no magic and is text is taken as a session file as it is (a person can paste one into a project); one of a later version is refused with the reason. A project whose session **cannot be loaded here** (a plugin that is not installed on this machine, a file that is not a session) gets a **new session in its place, and is saved as what it was given for as long as nothing in the new one is changed**: a project that is opened and saved on a machine that lacks a plugin does not lose the session.

#### How it is built

```
host's main thread ── Host ───────────────── activate / session_text / set_session_text / url
host's audio thread ─ Audio ── process(midi, input, output) ──► Renderer (Mutex) ──► AudioGraph ──► plugins inside
idle thread ───────── looks every ≥ 20 ms: no block since the last look? ─► Renderer::idle (takes the commands)
controller's thread ─ Controller + Runtime (the page's server) ◄── what the page asks, and Host's questions
```

- **The library and the plugin.** The package is a library (`src/lib.rs`: everything that `main.rs` held; `run` is its one public function besides the module `embed`) and a thin binary (`src/main.rs`: it ends the process). The plugin is a crate of its own in the workspace, `tang-clap` (a `cdylib` and an `rlib`; `clack-plugin` for the CLAP side, the library for everything else), so that a plain `cargo build` does not link a plugin. The channels between the audio thread and the rest are made in one place for the program and the plugin (`app::wiring::Wiring`). **The clack crates are pinned to one commit** (`rev = "57e89b3…"` in both manifests): the newest commit of the repository changed the host's API, and adding a new crate from that source had moved the lock to it without a word.
- **`tang::embed`.** `Host` is what the host's main thread has, one for each instance: `activate(rate, max_frames)` makes the engine (the renderer, the idle thread, and the controller's thread, which loads the session and serves the page) and gives the host's audio thread its end of it (`Audio`); `session_text` asks the controller's thread for the session as text (it reads out what is in the plugins inside first, as a save does: `Controller::session_text`); `set_session_text` is a session that the host gives. Activated again at the rate and the block size that it has, nothing is made again (what the page was editing goes on); at another, the session is read out and loaded again, since the plugins inside are loaded for a rate and a size. **A session that the host gives while the plugin plays is loaded under the handle that the audio thread already has** (the new engine takes the place of the renderer inside the same mutex), with the page going to another address.
- **The audio thread.** `Audio::process(midi, input, output)` puts the host's input where the audio inputs of the session read it (`HostInput`), has the renderer render the block with the host's events at their frames after the notes that the page played (`Renderer::render_planar`), and copies the engine's two channels into the host's buffers (a host that gives one channel has the left, one that gives more has the right again). It `try_lock`s the renderer and spins for a few microseconds at most; a block that cannot have it is silence. The plugin copies what comes in before it writes what goes out, since a host may give the input and the output as the same memory. **A block of no frames** is not a block: it is not rendered (the plugins inside are never given one), it is not counted for the idle thread (it takes no commands, so the idle thread goes on taking them), and the events that came with it are dropped, since they have no frame to be at (`Audio::process`); a block that has no audio port to play on is an error that the host is told of.
- **The idle thread.** The commands that the controller sends go through a channel that holds 64, and the controller waits for room in it when it is full; a host that is not calling `process` (a track that is switched off, an audio engine that is stopped, and `activate` itself, which loads the session before any block is asked for) would stop a page that is editing. A thread looks every 20 ms or two blocks, whichever is longer, whether a block has come since the last look, and if none has, has the engine take what is waiting (`Engine::idle`: the commands, the plugins that come and go, and the notes that the page played are dropped: they are not for a block that comes later).
- **The host is a source of notes.** What the host sends is the first MIDI device (`Source::device(0)`), which the controller calls `Host` (`embed::HOST_DEVICE`; a `DeviceWatcher` that has the one device), so that a lane can be wired to it, or not, as to any device; the page's own piano and keys are the keys' source, as ever.
- **The page.** The controller's thread serves the session as `tang serve` does (`web::runtime::Runtime`), on `127.0.0.1` and a port that the system picks. **A plugin's own window is not available inside a host** (`Controller::window_check` says why; the main thread is the host's), and the catalog of the installed plugins is **scanned when the first browser has come** (a scan loads every installed plugin, which is a thing to do in a host's process only when someone asks for the list; `TANG_NO_SCAN` leaves it out). Nothing opens a sound card or a MIDI port, installs a Ctrl+C handler, or turns the main run loop. **A page that cannot be served** (the system gave no port) **does not stop the plugin**: the controller's thread goes on without one (the session plays, and is the host's to keep), the log says why, and the window button and the switch below answer that there is no page.
- **The switch that opens the page.** The plugin's one parameter (`PAGE_PARAM`, id 0: **Open the page**, stepped, 0 or 1, automatable, shown as `Closed` and `Open`). A press is the host setting it from under a half to a half or more (setting it again to what it is, is not one, so that an automation lane that stays at 1 opens nothing more). **In a block** the audio thread sees it and opens nothing (a browser is not started on the audio thread): it asks the host to call the main thread back (`request_callback`), and `on_main_thread` opens the page and has the switch put back to 0, in the next block, as a `param_value` event in the block's output (the host shows it fall). **In a flush** (the host sets parameters while the plugin is not processing, on the main thread, or only wants them taken) the page is opened at once and the switch goes back at the end of the same flush. A press while the plugin has not started opens nothing, says why in the log, and the switch goes back all the same. Every instance opens its own page.
- **The file stays loaded (Windows).** The plugin starts threads (the idle thread, the controller's, the page's server) that can still be running a moment after the host has let go of the last instance, and a host that unloads a plugin's file when it has no instance of it takes the code of those threads away with it: the file pins itself in the process when the host loads it (`pin_library`: `GetModuleHandleExW` with the `PIN` flag), so that a thread that outlives its instance never runs code that is not there. The other systems have no pin (it is a no-op there).
- **The log.** A host has no terminal, so the plugin logs to a file: `tang-plugin.log` in the system's directory for temporary files (`%TEMP%` on Windows), shared by every plugin in every process (each line says which process wrote it), begun again when it is over a megabyte. The level is `RUST_LOG`'s, or info.

#### Building it and putting it where a DAW looks

- **Windows (Bitwig).** With Rust and Node installed: `cd web && npm ci && npm run build` (the page is what a release build embeds), then `cargo build --release -p tang-clap --no-default-features --features vst3` (the plugins that can be loaded inside Tang are VST3 and CLAP; LV2 needs a library that Windows has not). The library is `target\release\tang_clap.dll`; **copy it as `Tang.clap`** to `C:\Program Files\Common Files\CLAP\` (all users; needs administrator rights) or `%LOCALAPPDATA%\Programs\Common\CLAP\` (one user), and have Bitwig rescan (Settings → Plug-ins → Rescan, or restart it). The CI job `plugin` builds the same file on `windows-latest` and keeps it as the artifact **`Tang-clap-Windows`** (`Tang.clap`), the one to download when there is no Rust on the machine; it has the same job for macOS and Linux.
- **macOS.** `cargo build --release -p tang-clap`, then `tang-clap/bundle.sh release` makes `target/bundle/Tang.clap` (a bundle: a directory with the library and an `Info.plist`, **signed ad hoc**: a signature of no identity, which is enough for the Mac that built it), and `mkdir -p ~/Library/Audio/Plug-Ins/CLAP && rm -rf ~/Library/Audio/Plug-Ins/CLAP/Tang.clap && cp -R target/bundle/Tang.clap ~/Library/Audio/Plug-Ins/CLAP/` puts it where a DAW looks (remove an older copy first: macOS can kill a signed binary that is written over in place; the system's folder, `/Library/Audio/Plug-Ins/CLAP/`, needs administrator rights). Tang's own `tang enumerate plugins` lists both plugins from there (under `CLAP Plugins`, with the ids `io.github.apanloco.tang.instrument` and `io.github.apanloco.tang.effect`), and a session can say `plugin = "clap:io.github.apanloco.tang.instrument"`. The page of a plugin that is loaded in a host scans the installed plugins when its first browser has come, and so meets this file, which the host has loaded already: clack counts the calls of `init`, so that it is loaded once and let go of once more, which was checked by hand (the plugin inside Tang, found by its id, with the scan on: the catalog came back whole with `Tang` and `Tang FX` in it, and nothing was lost). A bundle for another Mac needs a signature with an identity and to be notarised (a Mac that is strict about plugins will say so). The library is for the architecture of the Mac that built it (arm64 here): a host that runs as x86_64, under Rosetta, cannot load it, and a universal one is two builds put together with `lipo` (not done). No DAW is installed on the Mac that this was built on, so it was not tried in one.
- **Linux.** The same, and `~/.clap/`.
- `tang describe /path/to/Tang.clap` loads the file as any CLAP plugin and says what it is, and a session whose `plugin` is that path plays Tang inside Tang (the file's first plugin is the instrument): the check that needs no DAW.

#### Using it in Bitwig

Put **Tang** on an instrument track (or **Tang FX** in a device chain), press the device's button for its window (the little window icon, if Bitwig shows one for it: that is the one thing here that was not tried): the browser opens on the page of that instance. **If the device has no such button, its parameters have one: set `Open the page` to on** (or click it in the device's parameter list or the remote controls page): the page opens and the switch falls back to off. Build there what Tang builds (the bar's `+ Lane`, effects, modulators, cables, modules), play notes from a clip or a keyboard, and save the project: the patch is in the project. Two instances in one project are two sessions with two pages. If neither opens the page, its address is in `tang-plugin.log` (`%TEMP%\tang-plugin.log` on Windows).

#### What it does not do yet

TODO: **parameters**: the plugin has one, **Open the page**, and nothing of the session is a parameter, so Bitwig cannot automate or modulate anything of what a person builds. The way is a fixed bank (16 to 32) of parameters mapped to the macros that are exposed (steps 110 and 111: a macro has a name and an `expose` flag), told to the host both ways (the page's change is a `param_value` event out; the host's automation is a `SetMacro`), since a host wants a fixed list.
TODO: **tempo and transport**: Tang has a tempo of its own (patterns, the LFOs and step sequencers that sync to it); the host's `Process::transport` (its tempo, whether it plays, where it is) is not read. A pattern or a synced LFO does not follow Bitwig's tempo.
TODO: **a window of the plugin's own**: a webview in a window of the host's (`gui` embedded: WebView2 on Windows, WKWebView on macOS) in place of a tab of the browser, with the size that the host gives it. The page is the same.
TODO: **latency**: the plugin reports none (the `latency` extension): a plugin inside that has latency, or a limiter that is put in (2 ms), delays the output by what the longest path to the mix has, which the host does not compensate for. The engine knows it (P3f); the host has to be told, and told again when it changes.
TODO: **the windows of the plugins inside**: a nested plugin's own editor (step 112) is the main thread's and the main thread is the host's, and the window layer is macOS only (nothing opens one on Windows): a nested plugin is edited by its parameters in the page.
TODO: **the events of a block that has no frames** are dropped (a host that sent a note with an empty block would lose the note): they should be kept for the next block, at its first frame (whether Bitwig ever sends such a block was not looked into).
TODO: **note expressions and MPE**: a CLAP note's own volume, pan and tuning, and a host that sends MPE as MIDI on member channels, are not told apart from plain notes by the plugin (Tang's lanes do route MPE by channel).
TODO: **the scan of the installed plugins in a process of its own** (f179): a plugin inside that crashes while it is scanned takes the host's process with it, and a scan is slow in a process that the host's run loop is turning.
TODO: **COM on Windows**: the controller's thread has not initialised COM, which some VST3 plugins need on the thread that loads them; the program's own main thread has not either, and the plugins that were tried load.
TODO: **the page's Save, Save As and Open** are the program's, and a plugin's session is the host's project's, with no file: **Save** is refused with a note (`Could not save the session: No session path — cannot save`), but **Save As** writes the file that is named beside the process's working directory (`save_as_path`: `.` when the session has no file), which for a DAW is wherever the DAW was started from (often a directory of its own program, that cannot be written to), and then that file is the session's file. The page should hide them, or Save As should write to `~/.config/tang/sessions/`, where the program saves a new session.
TODO: **the pin of the file on macOS and Linux** (`pin_library` does nothing there): a host that unloads the file while a thread of the plugin's still runs is the same fault there as on Windows (`RTLD_NODELETE`, or the linker's `-z nodelete`).
TODO: **a second audio input** (a sidechain) and more outputs for the effect and the instrument; **VST3 and AU** by wrapping this file (`clap-wrapper`); **signing and notarising** on macOS to give the file to anyone else.
TODO: **a page that survives a change of sample rate**: the engine is made again then and its page has another port.

#### Found on the way

- **A session of more than sixteen lanes with an effect each never finished loading** (and more than about twenty-one with none): the loader sends the audio thread a few commands for each lane through a channel that holds 64, and the engine was started after the load, so that the load waited for room in the channel for ever, at start, saying nothing (`run_session`; the loader's own doc said "the audio thread must be (or soon be) draining it"). Found by reading how the engine is started for a plugin; **fixed in its own commit** (`7ceda41`: the engine is started before the session is loaded), with a test through the real program (40 lanes: it timed out after a minute before, and takes 0.7 s now).
- **Adding a crate from a git source moved the lock of all the others from it**: `clack-plugin` was new to the lock, and cargo updated `clack-host` and its siblings to the newest commit, whose API is not the one Tang's CLAP host is written for (the build failed in `src/plugin/clap.rs`). The commit is pinned by `rev` in both manifests now.
- **Windows had no config directory for a program started by a DAW**: `HOME` is not set there (only a shell that a person starts sets it), and the library of modules and the new-session path need `~/.config/tang`; `USERPROFILE` is the home now (`config_dir_from`).

#### Decisions (D113; the user may overrule them)

(1) CLAP first, both an instrument and an effect in one file, with ids in the `io.github.apanloco` namespace. (2) The window is the page in the browser first; a webview in a window of the host's is a step of its own. (3) The master's limiter is out in a new plugin (2 ms of latency that cannot be told to the host). (4) The session is the state, as text, so that a project can be read by a person and by a later Tang. (5) The host is a device called `Host`, not the keys. (6) The scan of the installed plugins waits for the first browser. (7) No parameters of the session in the first version: the plan is the macros, and a first version that can be tried is worth more than one that has everything; the one parameter there is, **Open the page**, is there because it is not known that Bitwig shows a button for a window that the plugin shows itself, and every host shows the parameters. (8) The clack crates are pinned. (9) A block of no frames is not a block (not rendered, not counted, its events dropped): the simplest thing that cannot go wrong, until a host is known that sends notes in one. (10) The file pins itself in the process on Windows only, which is where it will be tried first; the other two systems wait for a reason.
