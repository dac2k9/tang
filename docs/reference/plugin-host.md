# Tang as a plugin in a DAW

Part of what `CLAUDE.md` holds as a front door: the plugin that Tang is in a DAW (step 113), which is built from the same library as the `tang` program. `CLAUDE.md` has the index of the reference files. The `TODO:` lines are where this is not done yet.

### The two plugins in `Tang.clap` (step 113, `tang-clap/`, `tang::embed`)

The user's ask, after the plugin's own window (step 112) was done: "would be possible to add a target to be able to build this as a VST or other plugin format that we can load into a daw?" (2026-11-05), and, asked which DAW: **"I mainly use bitwig, on windows, so thats where I want to try it. Lets try this next."** (2026-11-06). Bitwig loads CLAP natively and co-created it, so CLAP is the format; VST3 and AU would come from wrapping it (`clap-wrapper`), and are not built.

- **What the file has.** One file, `Tang.clap`, with two plugins in it: **Tang** (`io.github.apanloco.tang.instrument`; features `instrument`, `synthesizer`, `stereo`: notes in, what the session plays out) and **Tang FX** (`io.github.apanloco.tang.effect`; `audio-effect`, `stereo`: stereo audio in, what the session makes of it out). The ids are what a host keeps a plugin by in every project that has it: **they are never changed.** Both have a stereo output, one input of notes (the MIDI dialect is the preferred one, the CLAP dialect is understood: a note-on and a note-off, and a choke as a note-off; what a CLAP note says beyond that, its expressions, is not carried over) and a window; the effect has a stereo audio input as well.
- **What a new one is.** A new Tang is one lane with the oscillator (`builtin:osc`) and a new Tang FX is one lane with the audio input (`builtin:input`, which plays what the host gives the plugin to hear: no sound card is opened) that goes to the mix, so that it passes the sound through until a person builds something in the page. **The master's limiter is out of the sound in both** (`Kind::default_session`): a host works in floating point and has headroom, and the limiter holds the sound back by 2 ms, which a host that is not told of it cannot make up for (an effect would be late against its own dry sound). A person who wants it puts it in, in the page, and then has the 2 ms.
- **The window is the page** (step 114). A host that can put a plugin's face in a window of its own (that is what the format's embedded window is for, and Bitwig supports it; it was not tried here) is given **an embedded window**: `create` for the system's own API (`win32` on Windows, `cocoa` on macOS), `set_scale`, `get_size` (1100 x 720, a window that can be resized both ways between 480 x 320 and 16,384 a side), `set_parent` with the host's window, `show`; and the window is **a web view of the system** (WebView2 on Windows, WKWebView on macOS, through `wry`) at the address of the page of that instance (`http://127.0.0.1:<port>/`), which the plugin makes in the host's window and the host sizes. Every instance serves its own page on a port that the system picks, on this machine only (no token is needed there). Where the system has no web view for it (Linux; a Windows that has no WebView2 runtime) the window is **a floating one that the plugin shows itself**, as it was in step 113: `show` opens the page in the browser that the person has, `hide` does nothing, the address is in the log (`Web interface: …`) if nothing opens it, and `TANG_BROWSER` says another program to open it with (it is run with the address as its one argument). A host is given the one that it asks for (`is_api_supported`: a floating window on every system, an embedded one where there is a web view), and the one that the plugin would rather be asked for (`get_preferred_api`) is the window of the host's where there is a web view. The plugin also has **a parameter**, **Open the page** (below), which opens the page in the browser in any case: for a host that shows no window button, and for a person who wants the page in a browser tab as well.
- **The web view (`tang-clap/src/gui.rs`).** The order of the calls, the sizes and what the view shows are written against two small traits (`Maker` and `View`), so that tests with no window hold them (`Gui`: the calls in the order that a host makes them, the size that the host made the window, the scale, the page that the view shows and follows); `native` is the system's web view through `wry`, the one part that needs a screen. *A window that is asked for before the plugin is switched on* (a host starts a plugin when it is going to play it, which may come after a person opens the window) **shows a few words that say that Tang has not started, and gets the page when the instance has one**: `refresh_gui` after `activate`, and after a session that the host gives (which has the instance served at another address: the view goes there); a view that cannot be made says why in the log and is tried again at `show`. *Sizes:* a host counts **pixels on Windows and tells the plugin the scale** (`set_scale`: 1.5 for 150%) and points on macOS (which the system has scaled already), so the default size is scaled where it is pixels (1100 x 720 at 150% is 1650 x 1080, which is the room that the page has at 100%), the least size is scaled too, and a size that the host has made the window is what it is. *Found with wry 0.57:* a view on macOS asks its parent for its window and **panics if there is none**, so the plugin asks AppKit first (`ready`), makes the view at `show` if the host has not put its view in a window yet, and guards every call into wry (a panic is an error, not the end of the host's process); a view that is **focused** makes the program that holds it the active one, which the host's window is not Tang's to say, so the view is made unfocused, and it **accepts the first click** (a click on a window that is not the key one is for the page); WebView2 keeps its profile in a folder that is by default beside the program that uses it, a host's own directory that a person cannot write to, so the plugin gives it `%LOCALAPPDATA%\Tang\WebView2`. *Found with clack at the pinned commit:* its wrappers of `set_parent` and `set_size` answer `true` to the host **whatever the plugin returns** (the `is_ok()` inside is lost to an `is_some()` outside; `create`, `show` and `hide` are right), so a view that cannot be made is told to the host at `show`, which is right, and not at `set_parent`; the plugin says why in its log.
- **What is saved is the session.** The host's `state` is the session as the text of a session file, after nine bytes (`TANGSESS` and a version, 1) that say what it is: what a person builds in the page (lanes, effects, cables, modulators, a macro's name, the places of the nodes) and what the plugins inside keep in them (step 112, part C) go with the host's project and come back with it. State that has no magic and is text is taken as a session file as it is (a person can paste one into a project); one of a later version is refused with the reason. A project whose session **cannot be loaded here** (a plugin that is not installed on this machine, a file that is not a session) gets a **new session in its place, and is saved as what it was given for as long as nothing in the new one is changed**: a project that is opened and saved on a machine that lacks a plugin does not lose the session.

#### How it is built

```
host's main thread ── Host ───────────────── activate / session_text / set_session_text / url
host's audio thread ─ Audio ── process(midi, input, output) ──► Renderer (Mutex) ──► AudioGraph ──► plugins inside
idle thread ───────── looks every ≥ 20 ms: no block since the last look? ─► Renderer::idle (takes the commands)
controller's thread ─ Controller + Runtime (the page's server) ◄── what the page asks, and Host's questions
```

- **The library and the plugin.** The package is a library (`src/lib.rs`: everything that `main.rs` held; `run` is its one public function besides the module `embed`) and a thin binary (`src/main.rs`: it ends the process). The plugin is a crate of its own in the workspace, `tang-clap` (a `cdylib` and an `rlib`; `clack-plugin` for the CLAP side, the library for everything else), so that a plain `cargo build` does not link a plugin. The channels between the audio thread and the rest are made in one place for the program and the plugin (`app::wiring::Wiring`). **The clack crates are pinned to one commit** (`rev = "57e89b3…"` in both manifests): the newest commit of the repository changed the host's API, and adding a new crate from that source had moved the lock to it without a word.
- **`tang::embed`.** `Host` is what the host's main thread has, one for each instance: `activate(rate, max_frames)` makes the engine (the renderer, the idle thread, and the controller's thread, which loads the session and serves the page) and gives the host's audio thread its end of it (`Audio`); `session_text` asks the controller's thread for the session as text (it reads out what is in the plugins inside first, as a save does: `Controller::session_text`); `set_session_text` is a session that the host gives. Activated again at the rate and the block size that it has, nothing is made again (what the page was editing goes on); at another, the session is read out and loaded again, since the plugins inside are loaded for a rate and a size. **A session that the host gives while the plugin plays is loaded under the handle that the audio thread already has** (the new engine takes the place of the renderer inside the same mutex), with the page going to another address.
- **The audio thread.** `Audio::process(midi, input, output)` puts the host's input where the audio inputs of the session read it (`HostInput`), has the renderer render the block with the host's events at their frames after the notes that the page played (`Renderer::render_planar`), and copies the engine's two channels into the host's buffers (a host that gives one channel has the left, one that gives more has the right again). It `try_lock`s the renderer and spins for a few microseconds at most; a block that cannot have it is silence. The plugin copies what comes in before it writes what goes out, since a host may give the input and the output as the same memory. **A block of no frames** is not a block: it is not rendered (the plugins inside are never given one), it is not counted for the idle thread (it takes no commands, so the idle thread goes on taking them), and the events that came with it are dropped, since they have no frame to be at (`Audio::process`); a block that has no audio port to play on is an error that the host is told of.
- **The idle thread.** The commands that the controller sends go through a channel that holds 64, and the controller waits for room in it when it is full; a host that is not calling `process` (a track that is switched off, an audio engine that is stopped, and `activate` itself, which loads the session before any block is asked for) would stop a page that is editing. A thread looks every 20 ms or two blocks, whichever is longer, whether a block has come since the last look, and if none has, has the engine take what is waiting (`Engine::idle`: the commands, the plugins that come and go, and the notes that the page played are dropped: they are not for a block that comes later).
- **The host is a source of notes.** What the host sends is the first MIDI device (`Source::device(0)`), which the controller calls `Host` (`embed::HOST_DEVICE`; a `DeviceWatcher` that has the one device), so that a lane can be wired to it, or not, as to any device; the page's own piano and keys are the keys' source, as ever.
- **The page.** The controller's thread serves the session as `tang serve` does (`web::runtime::Runtime`), on `127.0.0.1` and a port that the system picks. **A plugin's own window is not available inside a host** (`Controller::window_check` says why; the main thread is the host's), and **the catalog lists the built-ins and the modules of the library at once, and the installed plugins only if `TANG_SCAN` is set** (a scan loads every installed plugin on a thread of its own and lets go of it, and a host's main thread turns the run loop all the time: a plugin of the JUCE kind that is loaded and let go of while it turns takes the process with it, f179. **Found again with the window**: `tang window Tang.clap` died in `juce::MessageQueue::runLoopSourceCallback` when the page, opened in the window, started the scan, which in step 113 it did when the first browser had come. A plugin does not scan by itself now; with `TANG_SCAN=1` in the host's environment it does, as it did, at that risk). Nothing opens a sound card or a MIDI port, installs a Ctrl+C handler, or turns the main run loop. **A page that cannot be served** (the system gave no port) **does not stop the plugin**: the controller's thread goes on without one (the session plays, and is the host's to keep), the log says why, and the window button and the switch below answer that there is no page.
- **The switch that opens the page.** The plugin's one parameter (`PAGE_PARAM`, id 0: **Open the page**, stepped, 0 or 1, automatable, shown as `Closed` and `Open`). A press is the host setting it from under a half to a half or more (setting it again to what it is, is not one, so that an automation lane that stays at 1 opens nothing more). **In a block** the audio thread sees it and opens nothing (a browser is not started on the audio thread): it asks the host to call the main thread back (`request_callback`), and `on_main_thread` opens the page and has the switch put back to 0, in the next block, as a `param_value` event in the block's output (the host shows it fall). **In a flush** (the host sets parameters while the plugin is not processing, on the main thread, or only wants them taken) the page is opened at once and the switch goes back at the end of the same flush. A press while the plugin has not started opens nothing, says why in the log, and the switch goes back all the same. Every instance opens its own page.
- **The file stays loaded (Windows).** The plugin starts threads (the idle thread, the controller's, the page's server) that can still be running a moment after the host has let go of the last instance, and a host that unloads a plugin's file when it has no instance of it takes the code of those threads away with it: the file pins itself in the process when the host loads it (`pin_library`: `GetModuleHandleExW` with the `PIN` flag), so that a thread that outlives its instance never runs code that is not there. The other systems have no pin (it is a no-op there).
- **The log.** A host has no terminal, so the plugin logs to a file: `tang-plugin.log` in the system's directory for temporary files (`%TEMP%` on Windows), shared by every plugin in every process (each line says which process wrote it), begun again when it is over a megabyte. The level is `RUST_LOG`'s, or info.

#### Building it and putting it where a DAW looks

- **Windows (Bitwig).** With Rust and Node installed: `cd web && npm ci && npm run build` (the page is what a release build embeds), then `cargo build --release -p tang-clap --no-default-features --features vst3` (the plugins that can be loaded inside Tang are VST3 and CLAP; LV2 needs a library that Windows has not). The library is `target\release\tang_clap.dll`; **copy it as `Tang.clap`** to `C:\Program Files\Common Files\CLAP\` (all users; needs administrator rights) or `%LOCALAPPDATA%\Programs\Common\CLAP\` (one user), and have Bitwig rescan (Settings → Plug-ins → Rescan, or restart it). The CI job `plugin` builds the same file on `windows-latest` and keeps it as the artifact **`Tang-clap-Windows`** (`Tang.clap`), the one to download when there is no Rust on the machine; it has the same job for macOS and Linux. Building should need nothing more for the window (`wry` links the loader of WebView2 itself; it was type-checked and linted for Windows from the Mac, and not built there); **running** it needs the WebView2 runtime (see Using it in Bitwig).
- **macOS.** `cargo build --release -p tang-clap`, then `tang-clap/bundle.sh release` makes `target/bundle/Tang.clap` (a bundle: a directory with the library and an `Info.plist`, **signed ad hoc**: a signature of no identity, which is enough for the Mac that built it), and `mkdir -p ~/Library/Audio/Plug-Ins/CLAP && rm -rf ~/Library/Audio/Plug-Ins/CLAP/Tang.clap && cp -R target/bundle/Tang.clap ~/Library/Audio/Plug-Ins/CLAP/` puts it where a DAW looks (remove an older copy first: macOS can kill a signed binary that is written over in place; the system's folder, `/Library/Audio/Plug-Ins/CLAP/`, needs administrator rights). Tang's own `tang enumerate plugins` lists both plugins from there (under `CLAP Plugins`, with the ids `io.github.apanloco.tang.instrument` and `io.github.apanloco.tang.effect`), and a session can say `plugin = "clap:io.github.apanloco.tang.instrument"`. The page of a plugin that is loaded in a host scans the installed plugins when its first browser has come, and so meets this file, which the host has loaded already: clack counts the calls of `init`, so that it is loaded once and let go of once more, which was checked by hand (the plugin inside Tang, found by its id, with the scan on: the catalog came back whole with `Tang` and `Tang FX` in it, and nothing was lost). A bundle for another Mac needs a signature with an identity and to be notarised (a Mac that is strict about plugins will say so). The library is for the architecture of the Mac that built it (arm64 here): a host that runs as x86_64, under Rosetta, cannot load it, and a universal one is two builds put together with `lipo` (not done). No DAW is installed on the Mac that this was built on, so it was not tried in one.
- **Linux.** The same, and `~/.clap/`.
- `tang describe /path/to/Tang.clap` loads the file as any CLAP plugin and says what it is, and a session whose `plugin` is that path plays Tang inside Tang (the file's first plugin is the instrument): the check that needs no DAW.

#### Using it in Bitwig

Put **Tang** on an instrument track (or **Tang FX** in a device chain) and press the device's button for its window (the little window icon: the plugin asks for an embedded window, which Bitwig should show a button for, as for every plugin that has one: not tried): Tang's page opens **in the host's window**, 1100 x 720, which the host can resize. Build there what Tang builds (the bar's `+ Lane`, effects, modulators, cables, modules), play notes from a clip or a keyboard, and save the project: the patch is in the project. Two instances in one project are two sessions with two pages. **The window needs the WebView2 runtime on Windows** (Windows 11 has it, and Windows 10 where Edge is up to date; Microsoft's "Evergreen" installer otherwise): without it the window is the page in the browser, which the button opens. **`Open…`** in the page's bar (step 115, part A) picks a session file (`.toml`) from the disk and makes it the session of this instance: the engine is made again with it, the window follows to the page's new address, and the host is told that the project has changed (`state.mark_dirty`), so that it is saved with the project; there is no undoing it. With libraries of sounds to list (below) it opens the picker instead, which has that chooser among its own.

**The picker of sounds** (step 116, "a more advanced loader/picker"): `Open…` opens a box that lists the sounds Tang can see, a section for each library, with a search, the arrow keys and Enter, and **From this computer…** for a file anywhere else. The libraries are the folder that sessions are saved to (`~/.config/tang/sessions`, or `%USERPROFILE%\.config\tang\sessions` on Windows, listed as **Saved sessions**) and the folders that `~/.config/tang/config.toml` names, one table for each:

```toml
[[sounds.folder]]
name = "Examples"            # optional: the folder's own name if it is left out
path = "~/tang/examples"     # a leading ~ is the home
```

The file is read each time that the plugin starts its session (a project that is opened, the plugin activated again, a sound that is opened), so a folder that is added is there the next time and not at once; a file that cannot be read, or has a table that is wrong, is left out with a note in `tang-plugin.log`, and the plugin plays. A folder is listed down to four folders deep, its `.toml` files, newest first; a file that is not a session is shown, greyed, with why. The page names no path: a sound is named by its library's id and its place inside it, and a file that a link leads out of the folder is not read. A library that is far away (a server that people upload sounds to, which Tang downloads from) is one more kind of library and not built (the TODO in `web-page.md`, step 116).

**`Open the page`**, the device's one parameter (set it to on, or click it in the device's parameter list or the remote controls page), opens the page in a browser tab in any case, and falls back to off. If nothing opens a page, its address is in `tang-plugin.log` (`%TEMP%\tang-plugin.log` on Windows), and the same file says when the window's web view was made and when its page had loaded (`The window's web view is made`, `The window's page has loaded`).

**Without a DAW, on a Mac:** `tang window ~/Library/Audio/Plug-Ins/CLAP/Tang.clap` opens the plugin's window by itself, in a window of Tang's own, as a host would (`--size 900x600` makes it that size once it is open, `--snapshot FILE` writes what is in it as a picture, `--tree` prints the views).

#### Found on the way

- **A session of more than sixteen lanes with an effect each never finished loading** (and more than about twenty-one with none): the loader sends the audio thread a few commands for each lane through a channel that holds 64, and the engine was started after the load, so that the load waited for room in the channel for ever, at start, saying nothing (`run_session`; the loader's own doc said "the audio thread must be (or soon be) draining it"). Found by reading how the engine is started for a plugin; **fixed in its own commit** (`7ceda41`: the engine is started before the session is loaded), with a test through the real program (40 lanes: it timed out after a minute before, and takes 0.7 s now).
- **Adding a crate from a git source moved the lock of all the others from it**: `clack-plugin` was new to the lock, and cargo updated `clack-host` and its siblings to the newest commit, whose API is not the one Tang's CLAP host is written for (the build failed in `src/plugin/clap.rs`). The commit is pinned by `rev` in both manifests now.
- **Windows had no config directory for a program started by a DAW**: `HOME` is not set there (only a shell that a person starts sets it), and the library of modules and the new-session path need `~/.config/tang`; `USERPROFILE` is the home now (`config_dir_from`).

- **The scan of the installed plugins crashed the process again, now through the window** (step 114): `tang window Tang.clap` opened the window, the page that was in it connected, the plugin's controller started the scan (step 113's "when the first browser has come"), which loaded ROLI's Airwave Player on the scan's thread, and the main thread's run loop (the probe's, as a host's) died in `juce::MessageQueue::runLoopSourceCallback`: f179, which the docs of step 112 had found for the program's own loops and which a host's main loop is, all the time. **Fixed by not scanning by itself** (`TANG_SCAN` says to; the built-ins and the modules are listed at once, without a plugin being loaded), with the way to have the installed plugins back written as a TODO.
- **Tang as a host ignored `request_callback`, so a plugin's main thread was never called** (step 115, found while building `Open…`: the user tries the plugin inside Tang itself). A CLAP plugin that wants something done on the host's main thread (a page that opens another session, the switch that opens the page, a JUCE plugin's work that is not for the audio thread) calls `request_callback` from any thread and the host calls `on_main_thread` when it can. `src/plugin/clap.rs` logged "ignored". #### Decisions (D113; the user may overrule them)

(1) CLAP first, both an instrument and an effect in one file, with ids in the `io.github.apanloco` namespace. (2) The window is the page in the browser first; a webview in a window of the host's is a step of its own. (3) The master's limiter is out in a new plugin (2 ms of latency that cannot be told to the host). (4) The session is the state, as text, so that a project can be read by a person and by a later Tang. (5) The host is a device called `Host`, not the keys. (6) The scan of the installed plugins waits for the first browser. (7) No parameters of the session in the first version: the plan is the macros, and a first version that can be tried is worth more than one that has everything; the one parameter there is, **Open the page**, is there because it is not known that Bitwig shows a button for a window that the plugin shows itself, and every host shows the parameters. (8) The clack crates are pinned. (9) A block of no frames is not a block (not rendered, not counted, its events dropped): the simplest thing that cannot go wrong, until a host is known that sends notes in one. (10) The file pins itself in the process on Windows only, which is where it will be tried first; the other two systems wait for a reason. **Step 114:** (11) The window is a web view in a window of the host's where the system has one (WebView2, WKWebView through `wry`: +121 crates in the lock, and `objc2` went from 0.6.3 to 0.6.5), and the page in the browser where it has none; the browser stays as a fallback and as the parameter `Open the page`. (12) A plugin does not scan the installed plugins by itself (f179): the built-ins and the modules are listed, and `TANG_SCAN` opts in. (13) A window that is opened before the plugin is switched on waits with a page that says so, and gets the page when there is one. (14) `tang window` opens a CLAP plugin's window, as a diagnostic. **Part C** (the user: "can you install it? I still cant open the UI"): the button on a CLAP node of a session opens it too, through the registry of the windows that the VST3 plugins have (the editor keeps a main-thread handle of the plugin, which is on the audio thread, and a token that says whether the plugin is still there); `tang window` and a session are one path. (16) **`Open…` replaces the whole session of the instance and asks nothing first** (step 115): there is no undo for it and no confirmation (`window.confirm` is not a thing that every web view has, and a refused one would make the button do nothing), and a program that is started with its file does not offer it (it would have to be made again from the outside: a restart of the engine, the controller and the server in one process; written down as a TODO). **The size is a decision too**: the page sends the text as one message, so the server reads up to 8 MiB from a connection that has been let in (the page says 4 MiB), where a connection that has not been is still cut at 64 KiB the moment its message is read (the transport reads a frame whole, so that is held in memory for a moment: up to 8 MiB for each of at most 32 connections, before the token). (15) A plugin that asks the host to hide its window has it closed (and made again when a person asks), and one that asks to show it is refused: a window is opened by a person.
